# QuakeSharp: working agreements

Faithful C# port of Quake (`reference/Quake/WinQuake`, v1.09). Read `design.md` before making changes; it is the
source of truth for scope, fidelity rules and milestones. Record new decisions in its §12 decision log.

## Commands

- Build: `dotnet build QuakeSharp.slnx`
- Test: `dotnet test --solution QuakeSharp.slnx` (Microsoft.Testing.Platform runner, configured in `global.json`)
- Tables: `dotnet run tools/codegen/GenerateTables.cs` regenerates the `*.g.cs` files from `reference/Quake`.
- Tools: `dotnet run --project tools/QuakeSharp.Tools` (identify, files, extract, dump-graphics, export-textures,
  texture-pack-check, texture-pack-finish); they refuse to write inside the repository.
- Shaders (`shaders/*.slang`) are compiled by the `QuakeSharp.Render.Vulkan` build with `slangc`: `SLANGC`, or the
  Vulkan SDK's through `VULKAN_SDK`. CI pins the Slang release and its SHA-256 in `.github/workflows/ci.yml`.
- Try the executable from a Quake folder (it looks for `id1/` in the current directory) with `-window`,
  `-vkvalidation` and `-quitafter <seconds>`; `-enhanced` / `-faithful` (or Scroll Lock) for the enhanced mode.
- Fidelity tests need `QUAKESHARP_QUAKE_DIR` (a folder with the original `id1/pak0.pak`, `id1/pak1.pak`; the mission
  packs' tests also `hipnotic/pak0.pak`, `rogue/pak0.pak`) and
  `QUAKESHARP_TRACE_DIR` (traces from the oracle in `tools/oracle`); otherwise they skip. When one fails, write
  QuakeSharp's trace of the same command line with `quakesharp-tools trace <quake-dir> <out> <oracle's args>`, find
  the first differing frame with `quakesharp-tools trace-compare`, then compare detail around it: `-tracedump <frame>`
  on both sides writes the entities field by field. Run the oracle from its own Quake folder (base directory ".").
- The enhanced mode (design.md §11.6): `EnhancedModeChangesNothing` runs the trace tests again with its capture on;
  `quakesharp-tools trace ... -traceenhanced` writes such a run's trace. With a GPU, `quakesharp-tools enhanced-shot
  <quake-dir> <out-dir> <frames> <trace args>` draws the enhanced frame beside the software frame and their differences
  (`warp` for <frames> lists the frames under water), and `enhanced-bench <quake-dir> <frame> <w>x<h> <trace args>`
  times it.
- The oracle (WinQuake 1.09's C, headless; see `tools/oracle/README.md`): `tools/oracle/Build-Oracle.ps1 -WorkDir
  <dir outside the repo>`, then `tools/oracle/Trace-Demos.ps1`. If its sources, `src/` or the patch change, rebuild
  and regenerate the traces. `-traceshot <frame>` and `quakesharp-tools shot2png` show a frame.
- `LibmTests` and `RandTests` keep hashes printed by the oracle's `numerics.exe`, `OracleUnitTests` those of
  `quake-oracle.exe -oracleunits` (`tools/oracle/src/units.c`); if the input sets change, change the C alike and take
  the new hashes from it. Mind the oracle's right-to-left argument order when mirroring C calls (design.md §3.2).
  `ScenarioTests` keeps the hashes of `quake-oracle.exe -oraclescenario tools/oracle/units/<file>`; when one differs,
  diff `-print`'s transcript with the `.transcript` file the test writes next to its assembly.
- Coverage: `tools/Coverage.ps1 -OutDir <dir outside the repo>` (with the two variables above) runs the fidelity tests
  with coverlet and writes `coverage.md`: what the traces reach of Core, file by file, and the methods and lines they
  don't.
- Engine code lives in `QuakeEngine`, a partial file per C module, with the C's names (design.md §6.2 rule 13).
  Every module WinQuake's game uses is ported (the stand-ins of `QuakeEngine.Pending.cs` are gone).

## Rules

- `reference/Quake` and `reference/musl` are read-only submodules. Never edit them; the oracle patches a copy.
- Translate, don't redesign: keep the original control flow and function boundaries; annotate ported methods with
  their origin, e.g. `// sv_phys.c: SV_Physics_Toss`.
- Enum members, constants and table data ported from C keep their original names (`svc_temp_entity`,
  `MOVETYPE_TOSS`, `OP_ADD_F`).
- `*.g.cs` files are generated by `tools/codegen`. Never edit them by hand; change the generator and re-run it.
- Floats as in the C (design.md §3.1): keep `float` vs `double` and C's promotion rules exactly (a `1.0` literal is
  a double in both languages; `0.5f` is not `0.5`); no `System.Numerics` vector math or `MathF` shortcuts in ported
  code; transcendental functions only through the engine's own libm; out-of-range float-to-int casts through the
  x86-semantics helper; `rand()` only through the engine's shared generator.
- No global mutable state; subsystem state lives on instances owned by the engine root.
- Core has no platform or GPU dependencies: no SDL, no Vulkan. Tests and CI never need a GPU.
- Never commit game data (`*.pak` is git-ignored) or anything extracted from it (dumps, traces, demos recorded from
  it). Rerelease ("KEX") data is not valid for fidelity tests; identify game data by MD5.
- A test project must contain at least one test (the runner fails on zero tests).
- Ask before adding external code or packages, or downloading anything new.

## Working with the user

- Commit finished work without asking, and push right after each commit once a remote exists. Creating or changing
  anything outward-facing (the GitHub repository, releases) needs the user's go-ahead first.
- Keep design.md the source of truth and its decision log current.
- Concise, plain-language updates while working.
